$root="C:\Program Files\nodejs\node_modules\@deepseek-ai\dsh\node_modules\@deepseek-ai"

本机 `dsh-code-review` 报了 conflicting，但宿主与它要求的 `0.1.5-rc.2` 精确一致。

## 2. PowerShell 5.1 的四个坑

### 2.1 中文会变乱码

```powershell
[Console]::OutputEncoding = [Text.Encoding]::UTF8
$env:PYTHONIOENCODING = 'utf-8'   # 跑 Python 工具时
```

注意这**只影响显示**。接口返回的字节是对的——之前测 API 时控制台显示
`åœ¨ä¸­åŠ¨å®¨…`，实际内容是正确的 UTF-8 中文。

### 2.2 `Set-Content` 会把 UTF-8 重写成 ANSI

这是**最容易造成静默数据损坏**的一个。改文件必须显式指定编码：

```powershell
[System.IO.File]::WriteAllText($p, $t, (New-Object Text.UTF8Encoding($false)))
```

`Set-Content` 在 PS 5.1 下会把无 BOM 的 UTF-8 当 ANSI 读再写回，中文注释和文档
全部变成乱码，而文件看起来「正常」。

### 2.3 调 API 时字符串转请求体会丢中文

```powershell
# 错 —— description 全变成 ?
Invoke-RestMethod $url -Body @{ description = '为 DeepSeek…' } | ConvertTo-Json

# 对 —— 显式 UTF-8 字节
$bytes = [Text.Encoding]::UTF8.GetBytes(($body | ConvertTo-Json -Compress))
Invoke-RestMethod $url -Body $bytes -ContentType 'application/json; charset=utf-8'
```

这个坑在给 GitHub 建仓库时踩过：仓库 description 变成
`? DeepSeek Harness ????????`，而 README 因为走 git 字节传输**完全没受影响**。
**先查损坏范围再下结论**——当时差点误判成文件全坏。

### 2.4 PS7 语法不可用

`Join-String`、`??` 等在 5.1 上不存在。写脚本时按 5.1 语法来。

### 2.5 heredoc 不存在

```powershell
git commit -F - <<'MSG'    # PS 里会报语法错
```

改用 `git commit -F <文件路径>`，先把消息写进文件（注意用 §2.2 的写法）。

## 3. git 在本机的行为

| 通道 | 状态 |
| --- | --- |
| `git` → `https://github.com:443` | **失败**，TCP 通但 `Recv failure: Connection was reset` |
| `git` → `git@github.com`（SSH） | **正常** |
| `Invoke-WebRequest` → `github.com` | 正常（与 git 走同一 IP，差别在 TLS/HTTP 指纹） |
| `raw.githubusercontent.com` / `codeload.github.com` | 走 CDN，可用（但某些仓库会 404） |
| `api.github.com` | 可用，但**需要 token**，SSH 不行 |

已配置 `http.sslbackend=schannel` 仍失败——不是 TLS 后端问题。

**结论：能用 SSH 就用 SSH。** SSH 通道还免去把 token 写进任何文件。

```powershell
$env:GIT_SSH_COMMAND='ssh -o StrictHostKeyChecking=accept-new -o BatchMode=yes'
git clone git@github.com:user/repo.git
```

**git 身份未配置**（`user.name` / `user.email` 均为空），首次提交前要设：

```powershell
git config user.name  "jijiwu3526"
git config user.email "jijiwu3526@users.noreply.github.com"   # 无主邮箱用这个形式
```

**`git push` 不能创建远程仓库。** `Repository not found` 通常意味着仓库**不存在**
而不是没权限——用 `git ls-remote` 确认时，看到该报错反而说明名字是空的。

## 5. 审核子代理：两个插件的分工

### 5.1 `dsh-code-review` —— 独立审查

`/review` 起一个**原生独立子代理**读 Git、源码、调用方和测试，报告回主会话。
审查者不接收预加载的仓库快照，自己去取上下文。

```powershell
dsh plugin --profile web add "@michengai/dsh-code-review@0.1.8" --save-exact --registry=https://registry.npmjs.org/
```

| 命令 | 作用 |
| --- | --- |
| `/review` | 打开范围选择（基线分支 / 未提交改动 / 指定 commit / 自定义） |
| `/review <指令>` | 带自定义焦点 |
| `/review-status` | 查看进度或最近一份报告 |
| `/review-cancel` | 取消选择或进行中的审查 |

**关键限制（作者自己写的）**：

> 审查指令要求不改代码，但**工具层并非全局只读**。实际行为取决于 DSH 权限与沙箱。
> `never` 审批策略会拒绝需要审批的操作。

也就是**不能把它当作安全隔离**，只能当作独立视角。报告默认存
`$DSH_HOME/code-review`。

### 5.2 `dsh-agent-teams` —— 机器可判定的质量门禁

这个才是「审核子代理」的完整形态。它把「多轮审查直到通过」从 prompt 协议
升级为**状态机强制**：

```
review 失败(verdict=needs_revision)
  → 自动创建 repair-round-N+1
  → 自动创建 review-round-N+1（必须换回原 reviewer）
  → 直到通过或达到 maxReviewRounds
```

机器强制的部分（不靠 persona 自觉）：

- 没有合同的实现/修复任务**不能创建**
- 没有验收证据的任务**不能 completed**
- `review` / `requirements` 没有 `verdict=pass` **不能 completed**
- `changed_paths` 越界**不能 completed**
- 验证命令失败只能 `failed`
- **实现者不能批准自己的实现**（下一轮 review 必须换回原 reviewer）

角色分工：`requirements-analyst` / `requirements-challenger` / `implementer` /
`test-engineer` / `correctness-reviewer` / `security-reviewer` / `scope-reviewer` /
`integrator`。

**已知边界**（第一版的诚实声明）：范围控制是**完成时审计**，不是宿主写入拦截。
成员在执行中仍可能用 bash 改范围外文件，只是完成时会被 `changed_paths` 抓住。

配置：

```yaml
- id: agent-teams
  config:
    stateDir: .agent-teams
    memberProvider: spawn
    memberMaxDepth: 0        # 成员不能再建子代理
    maxMembers: 8
    reviewPolicy:
      requirementsMinRounds: 1
      requirementsMaxRounds: 4
      codeMaxRounds: 3
      maxRepairAttempts: 2
      requiredReviewers: [correctness, security, scope]
```

### 5.3 怎么选

| 需求 | 用哪个 |
| --- | --- |
| 「帮我审一下这段改动」 | `dsh-code-review`，一条 `/review` |
| 「按需求→实现→验证→审查循环做，直到过」 | `dsh-agent-teams` 质量门禁 |
| 只要一个独立视角，不要它改代码 | `dsh-code-review` + `never` 审批策略 |

## 6. preset 层（叠加层，改不动宿主注入）

`agent.cordis.yml` 是**叠加层**。官方文档（`@deepseek-ai/dsh-agent-presets` README）：

> 没有本包时，会话只能回退到宿主组装挂载的内容。

preset 能加工具、能覆盖行配置，但**移不掉宿主已注入的工具**。
实测白名单 preset 单独用：117 → 101，几乎无效。

完整方法论见 `按任务定制预设.md`。

### 6.1 行 id ≠ 插件名

| 插件 | 真实行 id |
| --- | --- |
| `dsh-mnemon` | **`mnemon-bundle`**（包在 `cordis:group` 里） |
| `@michengai/dsh-code-review` | `michengai-code-review`（去掉了 `@`/scope） |

写错**静默无效**，不报错。

### 6.2 必填 config 只报第一个失败的行

```powershell
dsh --profile web --dump-config     # 找到对应 - id: <row>，把 config 整块抄过来
```

已知必填：

| 行 | 必填 config |
| --- | --- |
| `tool-fs-search` | `sampleOverCapGlobResults` |
| `tool-todo` | `allowParallelInProgress` |
| `tool-subagent` | `provider` / `toolName` / `backgroundMode` |
| `persona` | **`prefix` 必填**，即使内容都写在 `suffix` |

### 6.3 `tool-subagent-fork` 不是独立包

它是 `dsh-tool-subagent` **内部**的 row id。当包写会得到
`names a plugin that cannot be resolved`，而 `agentPresets/list` 仍显示 healthy
——只有真去建会话才暴露。

### 6.4 链接安装必须用绝对路径

```powershell
# 错 —— 会被多解析一层，写成 C:/Users/plugin-src/...，安装目录为空
dsh plugin --profile web add "link:../../plugin-src/dsh-local-bridge"

# 对
dsh plugin --profile web add "link:C:/Users/Administrator/.dsh/plugin-src/dsh-local-bridge"
```

症状是 DSH 警告「declares no dsh.bundle」，但 `package.json` 里的
`dsh.bundle.patch` 声明**完全正确**——是路径问题，不是 manifest 问题。

## 7. 会话与工作区

### 7.1 `--register-workspace` 不能省

```powershell
# 错 —— 只有 cwd，侧栏显示在「未分组」
dsh-session new --preset X --workspace-path "C:\some\dir"

# 对
dsh-session new --preset X --workspace-path "C:\some\dir" --register-workspace
```

返回值自查：错的只有 `{"cwd": ...}`，对的有 `{"workspaceId": ...}`。

### 7.2 删会话

`dsh-session` **没有删除子命令**。`session/cancel` 的参数形状未文档化，
typert 网关校验很严（试了三种都失败）。直接调插件的 loopback 路由：

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:3080/dsh-delete-session/delete' -Method Post `
  -ContentType 'application/json' -Body (@{sessionId='session-xxx'} | ConvertTo-Json)
```

返回 `{ok, removed, stopped, flushed, detached, workspaceDetached}`。
注意 `workspaceDetached: true` 表示这个工作区注册被一并摘掉了——
如果那个工作区本来就没别的会话，它等于消失了。

### 7.3 唯一可信的工具集验证方式

**不要相信配置，不要问模型**——实测同一预设在「问模型你有哪些工具」时
得到过 13 / 2 / 0 三种不同自述。

读会话日志里 DSH 发给模型的 `request/header`：

```python
import zstandard, json, io
d = zstandard.ZstdDecompressor()
with open(LOG, 'rb') as fh:          # session.v3.jsonl.zstd，是 zstd 压缩的
    with d.stream_reader(fh) as r:
        for line in io.TextIOWrapper(r, encoding='utf-8', errors='replace'):
            e = json.loads(line)
            if e.get('type') == 'request/header':
                print([x['name'] for x in e['data']['header']['tools']])
                break
```

日志路径：`~/.dsh/sessions/<workspace-key>/<session-id>/session.v3.jsonl.zstd`

`--dump-config` 也有局限：它看得到 `disabled: true` 是否合并，但看不到 preset 层的
最终效果。**以会话日志为准。**

## 9. 本仓库自测在 Windows 上的已知失败

`python -m unittest discover -s tests` → 67 项，**3 项失败**，全部是平台差异：

| 测试 | 原因 |
| --- | --- |
| `test_file_is_private` | 断言 `0o600`；NTFS 用 ACL，`st_mode` 返回 `0o666` |
| `test_remote_session_create_and_cookie_export` | `UnicodeDecodeError: 'gbk'`；测试用 `read_text()` 未指定 encoding |
| `test_stale_cookie_reauthenticates_from_token_url` | 认证时序相关，与平台无关但在此环境下不稳定 |

`cd plugin && node --test` → 32 项，**2 项失败**：
`is created owner-only (0600)`、`tightens permissions on a pre-existing loose file`
——同样是 Windows 没有 Unix 权限位。

功能本身正常：桥接密钥文件的所有者实测为 `BUILTIN\Administrators`。

**偶尔会看到 `OSError: [WinError 10055]`（缓冲区空间不足）** 导致一批 socket 测试
整体 `setUpClass` 失败——这是本机的瞬时网络栈问题，**重跑即恢复**。不要误判成代码回归。

| 站点 | 规模 |
